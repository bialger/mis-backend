# Ограничения данных БД относительно старого статического фронтенда

Следующие возможности **макета** не имеют полного аналога в схеме БД или требуют доработки бэкенда:

1. **Журнал движения склада** — отдельной таблицы движений ТМЦ (приход/расход/перемещение) нет; на экране «Движение» показано пояснение. Есть только текущие остатки (`inventory_item`).

2. **Точная сумма частичной оплаты** — в `payment` одно поле `amount` и перечисление `payment_status`; доли «оплачено при PARTIAL» в API для отчётов пока **оценочные** (упрощённая логика), не отдельная сумма в БД.

3. **Удовлетворённость пациентов** — в модели нет опросов/рейтингов; в отчётах поле `satisfactionRate` остаётся `null`.

4. **История статусов приёма** — выводится из `audit_log` по `entity_type = 'APPOINTMENT'` и `entity_id`. Пока записи в журнал при изменении приёма **не создаются автоматически** из кода приложения, список часто пустой.

5. **«Блокировка по дате» медицинской записи** — в `medical_record` нет полей «срок редактирования» / «backdate»; блокировка в UI привязана к **`is_signed`** (подпись).

6. **Онлайн-записи на дашборде как отдельная очередь** — источник записи есть (`appointment.source`), но отдельной таблицы «новых онлайн-заявок» нет.

7. **Согласия пациента** — отдельной сущности в REST-контроллерах в этом проекте нет; вкладка «Согласия» — заглушка.

При появлении миграций/триггеров для п.4 и п.1 интерфейс можно наполнить без смены вёрстки.
